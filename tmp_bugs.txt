【BUG-1】A1 变体正则 O(n^2) 灾难性回溯（P0，会让演示翻车）— 已修复
  位置：data/polish-rules.json（A1 变体「不重要重要的是」）+ backend/detector.py 变体循环
  修复前正则：([^，。；！？]+)不重要[，,]\s*(?:重要的是|真正重要的是|关键是)\s*([^，。；！？]+)
  原因：开头就是无限定长度的否定字符类，且前面没有任何锚点。
        文本里没有「不重要，」时，每个起点都要扫到结尾再回退，整体 O(n^2)。
        因为 [^，。；！？] 也放行英文字母，所以英文长文本同样中招。
  修复前实测（无中文标点的文本）：
      10,000 字 -> 0.41s
      20,000 字 -> 1.64s   （约 4 倍）
      40,000 字 -> 6.57s   （约 4 倍）
      60,000 字 -> 17.50s  （HTTP 请求已超时）
     300,000 字 -> >90s 超时
  英文实测（修复前）：20,000 字符 1.48s / 40,000 字符 5.95s
  影响：/api/detect、/api/polish、/api/pipeline、/api/agent/chat 全部受影响
  修法（两条，均不改变命中语义）：
        ① 字符类加上限并排除换行：{1,60} + [^，。；！？\n]
           —— 每个起点最多回溯 60 步，复杂度由 O(n^2) 降为 O(60n)；
           未加 (?<=…) 左锚点，因为「我认为价格不重要」这类前文无标点的句子
           加了锚点会漏检（宁可保召回，用上限换性能）。
        ② 变体新增可选 "prefilter" 字段，detector 先做关键词预筛：
           "不重要" 不在文本里就整条跳过，杜绝无谓全量扫描。
  修复后实测（无标点长文本）：
      10,000 字 -> 0.023s   20,000 字 -> 0.030s   40,000 字 -> 0.059s
      60,000 字 -> 0.093s   300,000 字 -> 0.457s（修复前 >90s 超时，约 200 倍）
  修复后实测（英文 20,000/40,000 字符）：0.014s / 0.029s
  修复后最坏情况（含「不重要」但无「重要的是」）：
      20,000 字 0.049s / 40,000 字 0.082s / 60,000 字 0.122s / 100,000 字 0.203s
      —— 线性增长，无二次爆炸
  召回回归（4 条全部仍命中，改写结果不变）：
      价格不重要，关键是性能。                     → 命中 1 条 → 润色「性能。」
      这个方案的设计细节不重要，真正重要的是落地效果。 → 命中 1 条 → 「落地效果。」
      我认为价格不重要，重要的是能不能用。           → 命中 1 条 → 「能不能用。」
      A 不重要，重要的是 B。                        → 命中 1 条 → 「B。」
  误报回归：这个问题很重要，关键是方法要对。 → 0 条（未因改动新增误报）

【BUG-2】detect / polish 同步阻塞事件循环（P0）— 已修复
  位置：backend/server.py api_detect、api_polish
  原因：detector.detect / rewriter.rewrite 是 CPU 密集同步调用，直接跑在 async 函数里。
        对照 api_pipeline 已经用了 asyncio.to_thread，但 detect/polish 漏了。
  修复前实测：发一个 60,000 字请求（耗时 17.5s），同时请求 /api/health
        -> 健康检查延迟 16.50s（整个服务被单请求拖死）
  影响：任何慢请求都会让全站接口一起卡住，包括健康检查
  修法：① api_detect 改 await asyncio.to_thread(detector.detect, req.text)；
        ② api_polish 把「检测→润色（英文先翻译）」整段抽成同步函数 _polish_sync，
           接口层 await asyncio.to_thread(_polish_sync, req.text, req.options)。
           注意：英文分支里的 translator.translate 也是同步 HTTP 调用，
           一并放进线程里，否则英文润色仍会阻塞事件循环。
  修复后实测：20 万无标点字 detect 耗时 0.45s，同期 /api/health 延迟
        188 / 158 / 24 / 2 / 2 ms，最大 188ms（修复前 16.5s）→ PASS
  响应结构回归：/api/polish 返回字段与修复前完全一致
        changes / original / polished / report / safety_failures /
        total_changes / translated_from；report 子字段 summary/hits/metrics/f_metrics
  英文分支回归（打桩 translator，零外网零额度）：translated_from='en'、
        translate 调用 1 次、润色生效；中文分支 translate 调用 0 次；options 透传正常

【BUG-9】历史记录持久化遇 localStorage 配额会中断（P2，已修复 2026-11-25）
  位置：frontend-vue/src/composables/useSettings.js（history / savedPapers 两个 watch）
  原因：setItem 没有 try/catch；history 条目存的是全文（text + polished），
        没有截断。单条 5 万字（原文+改文）实测占 293 KB，30 条约 8.6 MB，
        而浏览器 localStorage 上限约 5 MB。
  修复前实测（Node + 真实 Vue 3.5.46，40 万字符/条）：
        第 5 条写入时抛 QuotaExceededError，内存 5 条 / 磁盘只剩 4 条；
        Vue 打印 [Vue warn] Unhandled error during execution of watcher callback
        + Unhandled error during execution of scheduler flush
        之后所有历史写入全部失败，刷新后停在溢出前那几条
  已做修复：
        ① savedPapers 持久化包 try/catch（收藏本身是轻量字段，只做兜底）
        ② history 持久化改为「超限则折半裁剪最旧条目后重试」，
           直到写入成功或只剩 1 条（1 条仍存不下则放弃持久化、内存保留）
        ③ 发生裁剪时同步更新内存 history 并 toast「存储空间不足，已自动清理旧历史」，
           用 persistingHistory 标志位防 watch 递归
        ④ 内存与磁盘保持一致，不再出现「界面有 N 条、刷新只剩 N-1 条」
  修复后实测（同一压力场景，连写 8 条 40 万字）：
        自动裁到 2 条（约 4.8 MB），内存/磁盘一致，无 Unhandled 警告，

  仍未处理（低优先）：条目本身不截断，单条超长文本仍会吃掉大量配额，
        建议后续把 history 只存前 2000 字预览 + 原文另存 IndexedDB

【BUG-12】A1 在「不是A，而是B」上直接删 A，会反转语义（P1）— 已修复
  位置：backend/rewriter.py A1 主模式
  原因：规则注释已警告「禁止只删 A，而是」，但代码实现就是只留 B。
        A 承载对比信息时（不是改不出来，而是改出来一句坏话），删 A 后意思整个反掉。
  修复前：
        「我们需要找到一种平衡——不是改不出来，而是改出来一句坏话；不是删掉修饰成分…」
